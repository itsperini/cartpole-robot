From MuJoCo swing-up to robotics RL foundations

This project is a focused learning track for robotics reinforcement learning using one controllable system: a MuJoCo cart-pole with normalized continuous force control. The current chapter is robust state-based control: trained TD3, SAC, and PPO policies are preserved, then tested with noise, friction, disturbances, delay, and opt-in hardware-like control-loop profiles.

Current State

5D State observation: cart position, cart velocity, pole angle encoding, angular velocity
[-1, 1] Normalized action mapped to physical cart force
3 Trained baselines: TD3, SAC, and PPO

The environment starts with the pole hanging downward. The controller must push the cart to build energy, swing the pole upright, then stabilize near the top.

System Architecture

The active repo is intentionally small: one custom simulator, model-free baseline trainers, shared evaluation metrics, rendering tools, and timestamped artifacts. This keeps algorithm comparisons fair and repeatable.

What Model-Free Control Learns

Actor

The actor maps the current 5D state to one continuous action. In this project, that action is normalized to [-1, 1] and then scaled into cart force by the environment. 

obs_t -> actor -> action_t

Critics

TD3 trains two value estimators for the same state-action pair. SAC also uses critic networks, while PPO learns from batches of on-policy rollouts. 

critic(obs_t, action_t) -> value estimate
The important robotics lesson here is continuous control: instead of choosing left or right, the policy chooses how much force to apply.

Ticks, Latency, and Delay

In this project, a tick means one policy/control step. The MuJoCo model uses a 20 ms physics timestep and the environment advances two physics steps for each policy action, so one policy tick is 40 ms. A one-tick delay is roughly 40 ms; a two-tick delay is roughly 80 ms.

One tick

The policy observes or actuates one control step late. At the current 25 Hz policy rate, that is about 40 ms of sensor or command latency.

Two ticks

The policy uses information or commands from two control steps ago. At the current rate, that is about 80 ms of latency.

Real hardware

Measure timestamps from encoder sample, firmware filtering, host receipt, policy inference, command send, motor-driver update, and mechanical response. Convert that total delay into policy ticks by dividing by 40 ms.

What researchers do

Augment history

For constant delays, extend the policy input with recent actions and observations so the delayed problem becomes closer to a Markov state. This is the method used by the current TD3 delay-history policy.

Predict the present

Use a state estimator or learned dynamics predictor to infer the current hidden state from delayed observations and past actions.

Randomize and measure

Sim2real pipelines often randomize latency, friction, masses, actuator behavior, noise, and disturbances, then refine the simulator with real measurements before deployment.

Research pointers: At Human Speed, Addressing Signal Delay, Robotic RL Simulation Pipeline, and Athletic Loco-Manipulation Sim2Real.

Control-Loop Realism Profiles

Robust scenarios model environment variation. Control-loop profiles model the command and sensing interface around the policy. They are opt-in and default to none, so previous experiments remain reproducible.

Latency and jitter

policy_25hz_latency and policy_25hz_jitter test one-tick latency with optional timing variation at the current 25 Hz policy rate.

Hardware-safe loop

policy_25hz_hardware_safe adds action slew limits, deadband, observation filtering, and encoder-like quantization on top of mild timing effects.

Delay-history training

policy_25hz_hardware_delay combines two-tick delay with the same hardware-facing effects, meant for policies that receive observation and action history.

Prefer hardware_mild plus a control-loop profile when testing physical variation and timing together. Use hardware_delay plus a profile only as an intentional harsher delay stress test.

Robust Sim Before Hardware

The project now has a first robustness layer for pressure-testing trained policies before retraining or touching physical hardware. The real cart-pole will have noise, latency, imperfect calibration, friction, endstop constraints, and disturbances, so the simulator needs to expose those failure modes early.

Action and sensor noise

The sensor_noise, latency_mild, and delay scenarios add encoder-like noise, action noise, and delayed actions/observations.

Physical variation

The friction scenario isolates rail and hinge friction. The dynamics scenario adds mass, damping, gravity, and force-limit variation.

Disturbances

The pushes and combined scenarios inject cart and pole velocity impulses during the rollout.

The trainer can now run inside robustness scenarios. The project keeps these as separate chapters: push recovery, hardware randomization, and delay-aware control with observation/action history.

What this run taught

Training directly on pushes improved the disturbance case from the clean PPO's 75% success to 95% success over 20 evaluation episodes. Clean swing-up stayed solved, but delay, randomized dynamics, and combined stressors need separate training rather than one overloaded policy.

Disturbance rollouts

These videos use the same seed and the same pushes scenario. The overlay flashes when the simulator injects a cart/pole velocity impulse.

Hardware randomization

Since the firmware can choose the command interface, the simulator can keep a normalized action while the hardware controller later maps that to force, velocity, or acceleration. The useful sim step here is therefore parameter randomization: friction, damping, mass, force limits, small sensor/action noise, and pushes.

Current best hardware candidate

TD3 fine-tuned under hardware_mild reaches 100% success on clean, friction, dynamics, pushes, and hardware-mild evaluation, with stronger mild-latency behavior than the clean TD3 checkpoint. It still fails harsh two-step delay, so delay is treated as its own policy family.

Delay-aware control

Delay changes the problem: one delayed observation is no longer enough to know the real control state. The delay-aware policies therefore use a 23-value input: four recent 5D observations plus three previous commanded actions.

Result so far

The best delayed policy is TD3 with four observation frames and three previous actions. It reaches 95% success on delay, but only 60% on hardware_delay, so the next robustness step should combine delay history with hardware randomization instead of treating them as separate specialties.

Interpretation

This is not one universal policy. The hardware-randomized TD3 checkpoint is better for friction, mass, noise, and pushes without major latency. The delay-history TD3 checkpoint is better when the control loop has meaningful action and sensor delay.

Roadmap

Future Hardware Path

The real setup should come after the simulated controller is robust. Start with encoder state, not image-only control. Cameras become safer once the motor, endstop, homing, and watchdog behavior are reliable.

Cart sensing

Stepper position, pulley calibration, soft limits, and two endstops for homing.

Pole sensing

Rotary encoder angle and filtered angular velocity.

Control bridge

ROS 2 plus ros2_control to expose a safe action interface.

The learned policy should sit behind a safety supervisor: soft limits, velocity limits, endstop handling, missed-step detection, watchdog timeouts, and emergency stop behavior.

Runbook

Train TD3

uv run cartpole-robot-train --config configs/algorithms/td3.toml

Train SAC or PPO

uv run cartpole-robot-train --config configs/algorithms/sac.toml
uv run cartpole-robot-train --config configs/algorithms/ppo.toml

Evaluate a policy

uv run cartpole-robot-eval \
  --algo td3 \
  --model artifacts/runs/td3/<run-id>/best/best_model.zip

Compare reports

uv run cartpole-robot-compare \
  artifacts/runs/td3/<run-id>/eval_metrics.json \
  artifacts/runs/sac/<run-id>/eval_metrics.json \
  artifacts/runs/ppo/<run-id>/eval_metrics.json

Run robustness report

uv run cartpole-robot-robust-eval \
  --algo ppo \
  --model models/best/ppo_cartpole_swingup_best_20260629-010531.zip

Train push recovery

uv run cartpole-robot-train \
  --config configs/algorithms/ppo_robust_pushes.toml \
  --resume models/best/ppo_cartpole_swingup_best_20260629-010531.zip

Train hardware randomization

uv run cartpole-robot-train \
  --config configs/algorithms/td3_robust_hardware_mild.toml \
  --resume models/best/td3_cartpole_swingup_best_20260628-012620.zip

Train delay history

uv run cartpole-robot-train \
  --config configs/algorithms/td3_robust_delay_history.toml

Evaluate control-loop profile

uv run cartpole-robot-robust-eval \
  --algo td3 \
  --model models/best/td3_cartpole_swingup_delay_history_obs4_act3_best_20260629-023430.zip \
  --scenarios hardware_mild \
  --control-loop-profile policy_25hz_hardware_safe \
  --observation-history-steps 4 \
  --action-history-steps 3

Train realistic loop later

uv run cartpole-robot-train \
  --config configs/algorithms/td3_realistic_control_loop_history.toml

Watch a trained policy

uv run cartpole-robot-watch \
  --algo td3 \
  --model models/best/td3_cartpole_swingup_delay_history_obs4_act3_best_20260629-023430.zip \
  --scenario delay \
  --observation-history-steps 4 \
  --action-history-steps 3

Run a random rollout

uv run cartpole-robot --render --render-fps 25

Open TensorBoard

uv run tensorboard --logdir artifacts/runs
